# Algorithm ladders - classification and regression

The point of a "ladder" is that it's an argument, not a menu. Each rung exists because the previous rung had a specific, demonstrable weakness - the notebook should show that weakness with real numbers, not just assert it, and the move to the next rung should read as "because of that," not "next, let's also try."

**Before using this file, check what the course has actually confirmed-taught by now** (project knowledge: session notes, slide PDFs, transcripts). This file reflects a tree-based toolkit (decision trees, bagging/random forest, boosting) plus the standard regression counterparts. If later sessions add new families (neural networks, clustering used as a feature step, etc.), extend this file rather than reaching for an untaught method on instinct.

## Classification ladder

**Rung 1 - single decision tree.** Start here always. It's the most explainable model that exists (a flowchart of yes/no questions), it's the building block every later model in this ladder is made of, and its failure mode is diagnostic. Train one with no limits first - it will very likely overfit (perfect or near-perfect training score, meaningfully worse test score) because with no restriction it keeps asking questions until it has effectively memorized individual training rows. Then tune `max_depth` (or another regularization dial the course has covered - `min_weight_fraction_leaf`, `min_impurity_decrease`, `max_leaf_nodes`) over a real range, plot train vs. test performance against the dial, and pick the value where test performance peaks before it starts declining. That peak-then-decline shape *is* overfitting, drawn as a picture - don't skip plotting it just because the tuned number is the real deliverable.

**Rung 2 - bagging / random forest.** Move here because of a specific, nameable weakness of Rung 1: even tuned, a single tree is *fragile* - its entire structure hinges on which question wins at the top, so a slightly different training sample can produce a meaningfully different tree with different mistakes (statisticians call this high variance). Bagging's fix: train many trees in parallel, each on its own random bootstrap sample (sampling with replacement), and let them vote. A random forest is bagging's refined, built-in version, with the added twist that each tree also only considers a random subset of columns at each split - this is what keeps the trees genuinely different from each other rather than all leaning on the same one or two dominant features. Use enough trees that the vote is stable (100 is a reasonable default; note that 6-10 might appear in class materials purely to keep diagrams readable, not because it's the practical recommendation).

**Rung 3 - boosting (AdaBoost, then XGBoost).** Move here because of a different weakness, specific to Rung 2: the forest's trees never communicate, so voting cancels *random* disagreement between them but does nothing about mistakes the trees *share* - a systematic blind spot every tree in the forest independently falls into. Boosting's fix is a different philosophy entirely: train trees **in sequence**, where each new tree is trained specifically to correct the errors of the chain so far (like a tutor who reviews your last practice test and drills only what you got wrong).

Try AdaBoost first if the course introduced it first (it usually did) - it's the classic, original implementation, typically chaining very weak "stump" trees (`max_depth=1`). **Report its result honestly even if it loses** - a chain of one-question stumps is often too weak to capture how many features interact, and this exact honest result (AdaBoost losing to a plain tuned tree) showed up in my own coursework on the wine dataset. A negative result here is informative, not an embarrassment to hide.

Then try XGBoost - the modern, heavily optimized boosting implementation, and the one most likely to win outright. Give it the hyperparameter-tuning treatment (Rung 3 is normally where the notebook's "tune the strongest model" section lands): search `n_estimators` and `learning_rate` together as a small grid, since the two dials trade off against each other, with `max_depth` fixed at a modest value (boosting works by chaining many modest trees, not a few deep ones).

**Do not assume Rung 3 always wins.** If the forest or even the tuned tree beats boosting on the actual test numbers, say so plainly and figure out why (small dataset where variance was never the real problem, weak base learners, an unlucky grid) rather than quietly picking whichever result looks better for the narrative.

## Regression ladder

**Rung 1 - linear regression.** Start here for the equivalent diagnostic reason: it's the simplest, most interpretable model (a straight-line relationship between each feature and the target, describable in one sentence - "each additional year of X is associated with a $Y change"), and its failure mode (or success!) is informative either way. Score it with R² and at least one error-in-original-units metric (RMSE or MAE - see the tradeoff note below) on the held-out test set.

**Important:** do not assume linear regression is the "weak baseline to be beaten." In a diabetes-dataset exercise from my coursework, plain linear regression (R² ≈ 0.45) *beat* both a single decision tree (≈0.13, badly overfit) and XGBoost (≈0.37) outright. If that happens here too, that is the honest result to report and build the recommendation around - a simpler, more interpretable model winning is a legitimate, teachable outcome, not a sign something went wrong.

**Rung 2 - single decision tree regressor.** Move here to test whether the true relationship is non-linear in a way a straight line can't capture (thresholds, interactions, non-monotonic effects). An unregularized tree regressor will very likely overfit for the same reason its classification cousin does - tune `max_depth` the same way, plotting train vs. test error against depth to find where test performance stops improving.

**Rung 3 - ensemble (random forest regressor and/or XGBoost regressor).** Move here for the same fragility/systematic-error reasoning as the classification ladder - a single tree regressor is a fragile, high-variance model; bagging (random forest) smooths that out via voting-by-averaging, and boosting (XGBoost) specifically targets whatever error pattern survives the forest's averaging. Tune the strongest of these the same way as classification: a small grid over the dials that most directly trade off underfitting against overfitting for that model family.

**Metric choice for regression, explained honestly:**
- **R²** - the intuitive "percentage of the pattern explained" number; easy for a non-technical reader, but can be misleading in isolation since it's scale-free and says nothing about the actual size of a typical error.
- **RMSE (root mean squared error)** - in the target's original units, and penalizes large errors disproportionately hard (a few huge misses hurt this number much more than many small ones) - the right choice when large errors are especially costly in the business context.
- **MAE (mean absolute error)** - also in original units, treats all errors proportionally to their size rather than squaring them - the right choice when one metric shouldn't be dominated by a handful of outliers.

Pick based on what the target's distribution (Section 4 of the notebook) actually looks like and what the business framing (Section 2) says a "bad miss" costs - not by default habit. Report R² alongside whichever error metric is the headline, the same way classification notebooks report accuracy alongside the honest headline metric.
